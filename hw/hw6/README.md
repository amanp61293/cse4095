# Chopsticks AI Web Game

## Project Overview

This project is a browser-based version of the Chopsticks game. It uses the professor's Python program as the reference for the game rules and state behavior, then ports the game engine and AI to JavaScript.

The human can choose to play as Player A or Player B. The computer chooses its moves using a bottom-up dynamic-programming/minimax table rather than random or hard-coded moves. The page also includes a show/hide AI Analysis panel that displays the computer's current state, MAX/MIN role, legal moves considered, minimax values, selected move, and predicted result from Player A's perspective.

## How to Run the Game

Keep these files in the same project folder:

- `index.html`
- `style.css`
- `game.js`
- `ai.js`

Open `index.html` in a modern web browser. A simple static web server such as VS Code Live Server can also be used.

When the page opens:

1. Choose **Go First** to play as Player A, or **Go Second** to play as Player B.
2. On a human turn, click one active hand and then an active computer hand to attack.
3. Use **Redistribute** to view the legal redistribution choices generated by the game engine.
4. The computer automatically makes its DP/minimax move on its turn.
5. Use **Restart / New Game** to return to the first/second player selection.

## Game Rules

Each player has a left hand and a right hand. Each hand has a value from 0 through 4.

The initial game state is:

- Player A: `(1, 1)`
- Player B: `(1, 1)`

A hand with value `0` is inactive. A player loses when both of that player's hands are `0`.

During an attack, an active hand attacks an active opponent hand. The attacking hand's value is added to the opponent hand. If the sum is 5 or greater, the attacked hand becomes `0`.

Players may also redistribute fingers between their own two hands when the resulting state is legal according to the supplied game rules.

The game uses a maximum depth of 20 individual turns. If both players are still active when that depth is reached, the position is treated as a tie for this depth-limited search.

## State Representation

The JavaScript state keeps the same information as the Python reference:

```text
[
    [A_left, A_right],
    [B_left, B_right],
    level
]
```

For example:

```text
[[1, 1], [1, 1], 0]
```

The level also determines whose turn it is:

- even level: Player A
- odd level: Player B

Every legal move creates a new state with `level + 1`.

## `nextMoves()`

`nextMoves(state)` is in `game.js`. It is the JavaScript version of the professor's Python `next_moves()` function.

It returns all legal successor states for the current position. It:

- returns no moves if either player has already lost;
- generates Player A's moves on even levels;
- generates Player B's moves on odd levels;
- allows attacks only between active hands;
- uses `overflowSum()` for attack results;
- generates the legal redistributions from one hand to the other;
- removes duplicate resulting states.

The UI does not independently decide which attacks or redistributions are legal. It gets the possible states from `nextMoves()` and uses those states for the human controls.

## Minimax

All minimax values are stored from Player A's perspective:

- `1` = Player A can win with optimal play
- `0` = tie within the search depth
- `-1` = Player A loses with optimal play

Player A uses **MAX**, so on an even level the AI selects the successor with the largest value.

Player B uses **MIN**, so on an odd level the AI selects the successor with the smallest value.

The computer does not choose randomly. It uses the selected successor already stored in the DP table.

## Dynamic-Programming Table

`bestMoveDP(depth)` is in `ai.js`.

The table is built from the maximum depth backward toward level 0. At the maximum depth:

- A with `(0, 0)` gives value `-1`;
- B with `(0, 0)` gives value `1`;
- both at `(0, 0)` gives value `0`;
- if both players are still active, the value is `0` because the search limit was reached.

The algorithm then processes levels from `depth - 1` down to `0`. Because successor states are always one level deeper, their values have already been calculated.

Each entry stores:

```text
{
    value: minimax value,
    bestMove: selected successor state
}
```

For Player A, the stored move has the maximum successor value. For Player B, it has the minimum successor value.

## Testing Performed

During development, the following behavior was checked:

- initial state `((1,1),(1,1),0)`;
- states containing a zero hand;
- attacks that cause a hand to become `0`;
- legal redistribution;
- illegal selections leaving the state unchanged;
- terminal state where Player A loses;
- terminal state where Player B loses;
- a live state at the maximum depth being treated as a tie;
- computer playing as Player A;
- computer playing as Player B;
- restart/new game logic;
- AI positions where legal successors have different minimax values.

The JavaScript `nextMoves()` behavior was also compared with the professor's Python `next_moves()` over all 625 hand configurations for both turn parities, for 1,250 state comparisons total. The resulting legal-state sets had no mismatches.

The JavaScript DP recurrence was checked at depth 20 across the 13,125 state/level combinations. Terminal values, depth-limit ties, MAX choices, MIN choices, and selected successor values were checked with no recurrence errors found.

The responsive CSS contains layouts for wide screens, screens below 800 px, screens below 600 px, and very narrow screens below 380 px. The responsive rules were reviewed in the project code. A final manual browser-width check should still be done on the machine used for submission.

## Known Limitations

- The AI uses a fixed maximum search depth of 20 levels.
- A game that reaches the maximum depth with both players still active is treated as a tie within that search limit.
- The project implements the required human-versus-computer mode only.
- The responsive layout has been reviewed in code, but a final manual visual check at different browser widths is still recommended before submission.

## Reflection Questions

**14. Why does Player A maximize while Player B minimizes?**  
The values in the minimax table are always from Player A’s point of view. A value of `1` means Player A is expected to win, `0` means a tie, and `-1` means Player A is expected to lose. Because of that, Player A chooses the highest possible value, while Player B chooses the lowest value because that gives Player A the worst outcome.

**15. Why is the DP table built from the deepest level toward level 0?**  
Each state depends on the values of the states that can come after it. By starting at the deepest level first, those successor states already have known values when the earlier states are evaluated. This makes it possible to work backward until reaching level 0.

**16. Why can dynamic programming be substantially faster than recursively exploring the complete game tree?**  
The same Chopsticks state can be reached through different sequences of moves. A normal recursive search could calculate the result of the same state many times. Dynamic programming stores the result once and reuses it whenever that state appears again, which avoids repeated work.

**17. Why should the UI obtain legal moves from the game engine rather than independently implementing the rules?**  
Using the game engine keeps one consistent version of the rules. If the UI had its own separate attack and redistribution rules, the two versions could accidentally behave differently. Using `nextMoves()` as the source of legal moves helps make sure the UI and the AI follow the same rules.

**18. What part of the project did your AI assistant help with most?**  
The AI assistant helped me most with understanding and implementing the dynamic-programming and minimax logic. It also helped me compare the JavaScript version with the Python reference and connect the game logic to the web interface while keeping the required behavior.

**19. What AI-generated suggestion did you have to verify, modify, or reject?**  
One suggestion I had to modify involved adding a short delay before the computer made its move. After reviewing the assignment and testing the project, I realized the delay was not required and could create an unnecessary restart issue. I chose to remove the delay and keep the computer move immediate while preserving the required minimax behavior.
